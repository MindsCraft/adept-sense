User API

User API Guide

This document provide guideline on how to call user-facing API. The service APIs are NID OCR, name transliteration, name gender detection, and liveness verification.

Introduction

API KEY is required to access all the api which needs to be passed in the header x-api-key.

All parameters are passed in the request body as JSON. so the content type must be set to application/json.

All responses are in JSON format.

Tokens are consumed based on the API called. Each user has a token balance that can be checked via /api/v1/user/token/get. Tokens are deducted on each API call according to the endpoint's cost.

All API will return few standard fields in the response body.

  • ok: boolean indicating success or failure.
  • txId: unique transaction ID for tracing.
  • username: the username associated with the API key used.
  • tokensRemaining: number of tokens left after the request.
  • tokensUsed: number of tokens consumed by the request.
  • data: endpoint-specific response data (present on success).
  • error: error details (present on failure).

 

Use the base URL https://api.adeptsense.tech for all endpoints below.

Authentication & Headers

  • x-api-key (required for protected endpoints): 16-character user API key.
  • Content-Type: application/json for JSON POST bodies.

GET

/api/v1/user/ip/get

  • Returns the user's current IP allowlist configuration in data.ipAllowList.
  • If the user has no IP restrictions, ipAllowList will be "ALL". If restrictions are enabled, it will return an array of allowed IPs.
  • API can only be called from IP address listed in IPAllowList.
  • Returns the current ipAllowList.
  • Headers: x-api-key: <USER_API_KEY>
curl -X GET https://api.adeptsense.tech/api/v1/user/ip/get \
  -H "x-api-key: <USER_API_KEY>"

Expected 200 (example)

{
  "ok": true,
  "txId": "TX_...",
  "username": "alice",
  "tokensRemaining": 99990,
  "tokensUsed": 0,
  "data": {
    "ipAllowList": "ALL"
  }
}
POST

/api/v1/user/ip/register

  • Adds the caller's IPv4/IPv6 to ipAllowList. Existing entries remain.
  • This is a convenient way to register your IP address in IPAllowList.
  • This is a one-click way to add your current IP without needing to specify it manually.
  • Use this endpoint from the IP address you want to register.
  • to use this api you need to make sure IP restrictions is disabled meaing you are allowing ALL IP address.
  • After you have added all your IP addresses, it is adviced that you enable IP Restriction.
  • Strict IP parsing. If caller's IP cannot be determined or is invalid, returns 400 with error code INVALID_IP.
  • If caller's IP is already in the list, it will be reported in data.added but no error is thrown.
  • If caller's IP is added successfully, it will be returned in data.added.
  • If the list was previously "ALL", it will be replaced with an array containing the new IP.
  • Headers: x-api-key: <USER_API_KEY>
  • Body: none.
  • Returns the updated ipAllowList.
curl -X POST https://api.adeptsense.tech/api/v1/user/ip/register \
  -H "x-api-key: <USER_API_KEY>"

Expected 200 (example if caller is ::1)

{
  "ok": true,
  "txId": "TX_...",
  "username": "alice",
  "tokensRemaining": 99990,
  "tokensUsed": 0,
  "data": {
    "ipAllowList": ["::1"],
    "added": ["::1"]
  }
}
POST

/api/v1/user/ip/add

  • Adds one or more specified IP addresses to ipAllowList. Existing entries remain.
  • Use this endpoint to add specific IP addresses to your IP Allowlist. You can add multiple IPs in a single request.
  • If the list was previously "ALL", it will be replaced with an array containing the new IPs.
  • Both IPv4 and IPv6 addresses are supported.
  • Strict IP parsing (IPv4/IPv6). Invalid IP -> 400 (no list returned).
  • If an IP is already in the list, it will be reported in data.existed but no error is thrown.
  • If new IPs are added successfully, they will be returned in data.added.
  • Call /api/v1/user/ip/register first to add your current IP if you have IP restrictions enabled and want to add your current IP.
  • Headers: x-api-key: <USER_API_KEY>, Content-Type: application/json
  • Body: {"ips":["203.0.113.10","2001:db8::1"]} (or ipAllowList/ip).
  • Existing IPs reported in existed; new IPs added and returned.
curl -X POST https://api.adeptsense.tech/api/v1/user/ip/add \
  -H "x-api-key: <USER_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"ips":["203.0.113.10","2001:db8::1"]}'

Expected 200 (example)

{
  "ok": true,
  "txId": "TX_...",
  "username": "alice",
  "tokensRemaining": 99990,
  "tokensUsed": 0,
  "data": {
    "ipAllowList": [
      "203.0.113.10",
      "2001:db8::1"
    ],
    "added": [
      "203.0.113.10",
      "2001:db8::1"
    ],
    "existed": []
  }
}
POST

/api/v1/user/ip/remove

  • Removes one or more specified IP addresses from ipAllowList. If the list becomes empty, it will revert to "ALL".
  • Use this endpoint to remove specific IP addresses from your IP Allowlist. You can remove multiple IPs in a single request.
  • Both IPv4 and IPv6 addresses are supported.
  • Strict IP parsing (IPv4/IPv6). Invalid IP -> 400 (with existing list in details.ipAllowList).
  • If an IP is not in the list, it will be reported in data.notFound but no error is thrown.
  • If IPs are removed successfully, they will be returned in data.removed.
  • Headers: x-api-key: <USER_API_KEY>, Content-Type: application/json
  • Body: {"ips":["203.0.113.10"]} .
curl -X POST https://api.adeptsense.tech/api/v1/user/ip/remove \

POST

/api/v1/user/ip/restriction

  • Enables or disables IP restrictions. When enabled, only IPs in ipAllowList can access the API. When disabled, all IPs are allowed.
  • Call /api/v1/user/ip/register first when enabling restrictions to make sure yoyr current IP is in the List.
  • Strict mode: if enabling restrictions but current list is empty, returns 400 with error code IP_ALLOWLIST_EMPTY.
  • Headers: x-api-key: <USER_API_KEY>, Content-Type: application/json
  • Body: {"enable": true|false}
  • enable: true -> remove ALL (restrict to list).
  • enable: false -> add ALL (unrestricted).
curl -X POST https://api.adeptsense.tech/api/v1/user/ip/restriction \
  -H "x-api-key: <USER_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"enable":true}'

POST

/api/v1/ocr/nid

  • Performs OCR on NID front and back images, extracts structured fields, and returns names in both English and Bangla.
  • Supports two input methods: multipart form-data for direct image upload (recommended) and JSON with base64-encoded images.
  • Response includes extracted fields, missing fields (if any), OCR metadata, and optionally the raw OCR text.
  • Fields extracted include name, parents' names, date of birth, NID number, address, blood group, place of birth, and issue date.
  • Headers: x-api-key: <USER_API_KEY>
  • Consumes 2 tokens per request.
  • Input requires two images: front and back.
  • Query: ?raw=0 omits data.rawText from response.

Multipart Upload (recommended)

curl -X POST "https://api.adeptsense.tech/api/v1/ocr/nid?raw=1" \
  -H "x-api-key: <USER_API_KEY>" \
  -F "front=@/path/to/front.jpg" \
  -F "back=@/path/to/back.jpg"

JSON Base64 Input

curl -X POST "https://api.adeptsense.tech/api/v1/ocr/nid?raw=0" \
  -H "x-api-key: <USER_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "front":"<base64-or-data-uri>",
    "back":"<base64-or-data-uri>"
  }'

Common OCR Errors

  • NO_TOKENS: user does not have enough tokens (needs 2).
  • OCR_PROVIDER_ERROR: Vision OCR provider call failed.
  • TRANSLITERATION_PROVIDER_ERROR: Bangla-name transliteration call failed.
  • PAYLOAD_TOO_LARGE: image exceeds upload limit.
POST

/api/v1/liveness/create

  • Creates a one-time liveness session and returns a hosted URL.
  • Headers: x-api-key: <USER_API_KEY>, Content-Type: application/json or multipart/form-data
  • Returned URL opens the hosted page at /liveness?token=....
  • Liveness now performs only liveness verification. Face match is no longer part of this flow.
  • Optional body field: "debug": true adds &debug=1 to the returned hosted URL.
  • Optional body field: "callbackUrl" lets the server push the final liveness result to your backend after storage.
curl -k -X POST "https://api.adeptsense.tech/api/v1/liveness/create" \
  -H "x-api-key: <USER_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "userId": "user-123",
    "platform": "web",
    "callbackUrl": "https://example.com/liveness-callback",
    "debug": true
  }'

Hosted URL

/liveness?token=...

  • This is the hosted liveness page URL returned by /api/v1/liveness/create.
  • Open this URL in a browser, webview, or host app to start the liveness workflow.
  • The token query parameter is required. It identifies the one-time liveness session.
  • The hosted page performs only liveness verification and posts the final liveness result back to server.
  • The stored result can then be fetched using /api/v1/liveness/result.
  • The hosted page can also emit the liveness result to the host app.
  • Optional query parameter: debug=1.
https://api.adeptsense.tech/liveness?token=eyJzaWQiOiI3OT&debug=1

Notes

- token=... starts the specific one-time liveness session.
- debug=1 only enables the visible debug toggle/button on the hosted page.
- If debug is not needed, open the URL without &debug=1.

/api/v1/match/face/submit

  • Creates a new async face-match task and returns immediately with a taskId.

NID OCR Guideline
Guide

NID OCR Step By Step Guide

  • Use this guide when you want to understand how to send front and back NID card images and consume the parsed OCR result.
  • The OCR understands three NID formats: 17 digit, 13 digit, and 10 digit.
  • From the back side, other than address, it can retrieve issue date and blood group if available.
  • It also transliterates mother and father or husband name from Bangla to English.

Core Idea

OCR API GUIDE
=============

Core idea behind this API is to pass front and back side of NID card and perform OCR on them.
The OCR understands three type of NID. It includes 17 digit, 13 digit and 10 digit version.
From back side other than address, it can retrieve issue date and blood group if available.
This will also perform transliteration of Mother and father (husband) name from Bangla to English.

Overview

The OCR API for Bangladesh NID is:

POST /api/v1/ocr/nid

It:
- performs OCR on front and back images
- parses structured NID fields
- optionally returns raw OCR text

Supported input methods:
- multipart/form-data file upload
- JSON with base64 images

Authentication

x-api-key: YOUR_API_KEY

Endpoint

Production:
https://api.adeptsense.tech/api/v1/ocr/nid

raw Parameter

Use:
- raw=1
  Returns structured parsed response inclduing full raw OCR text for front and back images

- raw=0
  Returns structured parsed response without raw OCR text

Examples:
- /api/v1/ocr/nid?raw=1
- /api/v1/ocr/nid?raw=0

Required Input

You must send both images:
- front
- back

Accepted input names internally include aliases, but recommended names are:
- front
- back

CURL Example: Multipart Upload

curl -X POST "https://api.adeptsense.tech/api/v1/ocr/nid?raw=1" \
  -H "x-api-key: <USER_API_KEY>" \
  -F "front=@/absolute/path/front.jpg" \
  -F "back=@/absolute/path/back.jpg"

CURL Example: JSON Base64 Upload

curl -X POST "https://api.adeptsense.tech/api/v1/ocr/nid?raw=0" \
  -H "x-api-key: <USER_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "front": "BASE64_FRONT_IMAGE",
    "back": "BASE64_BACK_IMAGE"
  }'

You may also send data URI:

{
  "front": "data:image/jpeg;base64,/9j/4AAQSkZJRgABAQ...",
  "back": "data:image/jpeg;base64,/9j/4AAQSkZJRgABAQ..."
}

What OCR API Does Internally

1. Validates front and back image input
2. Runs OCR on front image
3. Runs OCR on back image
4. Parses Bangladeshi NID fields
5. Normalizes selected values such as DOB
6. Romanizes Bangla parent names where needed
7. Returns parsed structured result
8. If raw=1, includes raw front/back OCR text

Structured Response Fields

Typical top-level output:
- fields
- missingFields
- meta
- normalized
- rawText (only when raw=1)

Typical fields:
- name_bn
- name_en
- father_or_husband_bn
- father_or_husband_en
- mother_bn
- mother_en
- dob_en
- issue_date_en
- nid_number

Typical normalized output:
- dob_iso
- issue_date_iso

meta contains:
- requestId
- timingsMs
- headerChecks
- relationship

NID Number Parsing Rules

The parser supports:
- 10 digit NID
- 13 digit NID
- 17 digit NID

Special note:
- for 17 digit NID, the first 4 digits are expected to match DOB year when available

Node.js Example: Multipart File Upload

import fs from "node:fs/promises";

const apiKey = process.env.API_KEY;
const baseUrl = "https://api.adeptsense.tech";

async function runOcrMultipart() {
  const frontBuffer = await fs.readFile("./front.jpg");
  const backBuffer = await fs.readFile("./back.jpg");

  const form = new FormData();
  form.append("front", new Blob([frontBuffer], { type: "image/jpeg" }), "front.jpg");
  form.append("back", new Blob([backBuffer], { type: "image/jpeg" }), "back.jpg");

  const response = await fetch(`${baseUrl}/api/v1/ocr/nid?raw=1`, {
    method: "POST",
    headers: {
      "x-api-key": apiKey
    },
    body: form
  });

  const json = await response.json();
  if (!response.ok) {
    throw new Error(JSON.stringify(json, null, 2));
  }

  console.log(JSON.stringify(json.data, null, 2));
}

runOcrMultipart().catch(console.error);

Practical OCR Guidelines

For best OCR quality:
- keep the full card visible
- avoid blur
- avoid glare or reflection
- keep text horizontal when possible
- use front and back images clearly
- do not crop important fields

For NID OCR specifically:
- front image is critical for name, DOB, NID number
- back image helps with additional consistency and data capture
- data.headerChecks field from result could be used to validate whether the provided
  card is a valid Bangladesh NID card

Error Handling Notes

Common situations:
- missing front image
- missing back image
- invalid base64
- invalid API key
- insufficient user tokens

Recommended handling:
- always parse JSON response
- if response.ok is false, inspect:
  - error.code
  - error.message

Recommended Implementation Pattern

1. Collect front and back image
2. Optionally compress or resize
3. Choose transport:
   - multipart file
   - base64 JSON
4. Call /api/v1/ocr/nid
5. Read:
   - fields
   - normalized
   - missingFields
6. If debugging OCR issue, call with raw=1
7. Inspect rawText to understand parse problems
8. validate JSON data.headerChecks to confirm the card is Bangladesh NID
   "headerChecks": {
       "government_bn": true,
       "government_en": true,
       "national_id_bn": true,
       "national_id_en": true
     }

Liveness Verification Guideline
Guide

Liveness Verification Step By Step Guide

  • Use this guide when you want to create a liveness session, open the hosted liveness URL, and receive the final liveness result correctly.
  • The most important identifiers are token for the hosted URL and sessionId for stored result retrieval.
  • Liveness now performs only liveness verification. Face match is handled by a separate API.

Core Idea

LIVENESS API GUIDE
==================

Core idea behind how liveness works is that developer creates a one-time liveness session by calling
/api/v1/liveness/create . This returns a hosted URL based on a one-time token.
The hosted URL looks like /liveness?token=...
The token can be used one time for a limited time.
/api/v1/liveness/create also returns sessionId which is used to retrieve the stored result later.

Liveness now performs ONLY liveness verification.
The final selfie captured at the last step of the liveness workflow is stored in the liveness result.
If developer wants face matching, developer should call the separate face match API with:
- reference image
- selfie image from liveness result

Overview

1. POST /api/v1/liveness/create
   1a. optional: include callbackUrl
   1b. optional: include debug=true
2. Save:
   - sessionId
   - url
3. Open returned hosted URL: /liveness?token=...
4. User completes liveness
5. Hosted flow submits final liveness result to server
6. Server stores result
7. Receive result via:
   - embedded host app
   - callback URL
   - /api/v1/liveness/result?sessionId=...

Main Endpoints

1. POST /api/v1/liveness/create
2. GET /api/v1/liveness/result?sessionId=...

Three Ways To Receive Result

Method A. Host app
- hosted liveness page emits the liveness result to host app
- includes selfie

Method B. callbackUrl
- server pushes the final stored liveness result to your backend

Method C. result API
- fetch /api/v1/liveness/result?sessionId=...
- returns the stored liveness result with selfie

Face Match Guideline
Guide

Face Match Step By Step Guide

  • Use this guide when you want to compare a reference image and a selfie image using the async face match API.
  • The most important identifier is taskId returned by /api/v1/match/face/submit.
  • Recommended production pattern is to take the selfie from completed liveness result and then call the face match API separately.

Core Idea

FACE MATCH API GUIDE
====================

Core idea behind face match is that developer submits two images:
- reference image
- selfie image

These images are submitted to the async API:
/api/v1/match/face/submit

The API returns immediately with a taskId.
The face match work continues asynchronously on the server.
Developer can then:
- wait for server callback if callbackUrl was provided
- or poll /api/v1/match/face/result?taskId=...

Recommended production pattern is:
1. perform liveness
2. collect selfie from liveness result
3. call face match submit with:
   - reference image (Ex. from Election Commssion Response)
   - selfie from liveness result

Overview

1. POST /api/v1/match/face/submit
   1a. include referenceImage
   1b. include selfieImage
   1c. optional: include callbackUrl
2. Save taskId
3. Server queues the task and returns immediately
4. Background worker processes the task
5. You receive result in one or both ways:
   5a. callback URL receives final result if provided
   5b. GET /api/v1/match/face/result?taskId=... returns current or final result

Important:
- This endpoint consumes tokens when submit is accepted
- Result can be:
  - queued
  - in_progress
  - completed
  - failed
- completed means matching finished successfully from a technical point of view
- PASS or FAIL is found in result.result and result.matched

Main Endpoints

1. POST /api/v1/match/face/submit
   Creates a new async face match task and returns taskId immediately.

2. GET /api/v1/match/face/result?taskId=...
   Returns current or final task result.

Authentication

Use:

  x-api-key: YOUR_API_KEY

This is required for:
- /api/v1/match/face/submit
- /api/v1/match/face/result

Submit API Input Fields

Required:
- referenceImage
- selfieImage

Optional:
- callbackUrl

Image input can be sent:
- as multipart file upload
- as JSON base64
- as data URL

Recommended field names:
- referenceImage
- selfieImage

Accepted aliases also include:
- reference
- selfie
- referenceImageBase64
- selfieImageBase64

What Submit API Returns

The submit API returns:
- taskId
- status
- createdAt
- updatedAt
- completedAt
- expiresAt
- callbackUrl
- callbackPending
- callbackDelivered
- result

Initial result is:
- status = queued
- result.status = in_progress
- result.result = PENDING

Result API Behavior

If task is not finished yet:
- status may be queued or in_progress
- result shows:
  - status: in_progress
  - result: PENDING

If task finished:
- status is completed or failed
- result contains:
  - matched
  - confidence
  - threshold
  - matchConfidenceLevel
  - descriptor section
  - landmark section

Callback Behavior

If callbackUrl was provided in submit API:
- server posts the final task payload to callback URL after task is completed or failed

Callback payload includes:
- taskId
- status
- createdAt
- updatedAt
- completedAt
- expiresAt
- callbackUrl
- deliveryContext = callback_push
- result

Callback payload does NOT include:
- callbackPending
- callbackDelivered

Those two fields are only useful when you later fetch the task by calling
/api/v1/match/face/result?taskId=...

Typical Submit Response

Detailed Usage Guideline: Submit

Production endpoint:
  https://api.adeptsense.tech/api/v1/match/face/submit

Authentication header:
  x-api-key: YOUR_API_KEY

Method:
  POST

Required inputs:
- referenceImage
- selfieImage

Optional input:
- callbackUrl

Supported submit formats:

A. multipart/form-data
   Best when you already have image files on disk.

B. application/json
   Best when frontend or backend already has base64 image data.

JSON base64 body may use:
- referenceImage: "BASE64_STRING"
- selfieImage: "BASE64_STRING"

or object form:
- referenceImage: { "base64": "BASE64_STRING", "mimeType": "image/jpeg" }
- selfieImage: { "base64": "BASE64_STRING", "mimeType": "image/jpeg" }

or data URL form:
- referenceImage: "data:image/jpeg;base64,..."
- selfieImage: "data:image/jpeg;base64,..."

Important submit notes:
- submit is asynchronous
- accepted submit returns taskId immediately
- save taskId in your database or transaction log
- tokens are consumed when submit is accepted
- if callbackUrl is provided, server posts final result payload to that URL
- callbackUrl must be a valid http:// or https:// URL

What to do after submit:
1. store taskId
2. optionally wait for callback
3. or poll /api/v1/match/face/result?taskId=...

  }'

Typical submit success handling:
- read response.data.taskId
- read response.tokensRemaining
- poll result API or wait for callback

Node.js Example: Submit Face Match

import fs from "node:fs/promises";

const apiKey = process.env.API_KEY;
const baseUrl = "https://api.adeptsense.tech";

async function submitFaceMatch() {
  const referenceBuffer = await fs.readFile("./reference.jpg");
  const selfieBuffer = await fs.readFile("./selfie.jpg");

  const form = new FormData();
  form.append(
    "referenceImage",
    new Blob([referenceBuffer], { type: "image/jpeg" }),
    "reference.jpg"
  );
  form.append(
    "selfieImage",
    new Blob([selfieBuffer], { type: "image/jpeg" }),
    "selfie.jpg"
  );
  form.append("callbackUrl", "https://example.com/facematch-callback");

  const response = await fetch(`${baseUrl}/api/v1/match/face/submit`, {
    method: "POST",
    headers: {
      "x-api-key": apiKey
    },
    body: form
  });

  const json = await response.json();
  if (!response.ok) {
    throw new Error(JSON.stringify(json, null, 2));
  }

  console.log("taskId:", json.data.taskId);
  console.log("status:", json.data.status);
  console.log("tokensRemaining:", json.tokensRemaining);
}

Detailed Usage Guideline: Result

Production endpoint:
  https://api.adeptsense.tech/api/v1/match/face/result

Authentication header:
  x-api-key: YOUR_API_KEY

Method:
  GET

Required query parameter:
- taskId

Example:
  /api/v1/match/face/result?taskId=5190bb5e-0839-49ad-9027-c66d03e64d6f

Result API rules:
- use the same user API key that created the task
- a different user cannot read another user's task
- if task is still running, response data.status may be queued or in_progress
- while task is still running, response data.result.result is PENDING
- when work is finished, response data.status becomes completed or failed
- if task has expired, server returns 410
- if taskId is missing, server returns 400
- if taskId is unknown, server returns 404

Recommended polling pattern:
1. call submit API
2. save taskId
3. wait 1 to 2 seconds
4. call result API
5. if status is queued or in_progress, wait again and retry
6. stop polling when status becomes completed or failed

What to inspect in final result:
- data.status
- data.result.result
- data.result.matched
- data.result.confidence
- data.result.threshold
- data.result.matchConfidenceLevel
- data.result.descriptor
- data.result.landmark

CURL Example: Get Face Match Result

curl -G "https://api.adeptsense.tech/api/v1/match/face/result" \
  -H "x-api-key: YOUR_API_KEY" \
  --data-urlencode "taskId=5190bb5e-0839-49ad-9027-c66d03e64d6f"

Typical client logic:
- if response.data.result.result == PENDING then keep polling
- if response.data.result.result == PASS then treat as matched
- if response.data.result.result == FAIL then treat as not matched or technically failed depending on error

Quick Summary

Recommended pattern:
- do liveness first
- retrieve selfie from liveness result
- submit face match request
- use callback OR result API with taskId

Submit endpoint:
- POST /api/v1/match/face/submit
- returns taskId immediately
- accepts referenceImage and selfieImage

Result endpoint:
- GET /api/v1/match/face/result?taskId=...
- poll until status becomes completed or failed

Do not block liveness UX waiting for face match.
